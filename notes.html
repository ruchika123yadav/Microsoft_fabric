What is Microsoft Fabric?

Microsoft Fabric is an all-in-one, SaaS analytics platform that covers the entire data journey — moving data, transforming it, storing it, analysing it in real time, doing data science on it, and visualising it — all in one place, on one shared copy of data.

⭐ Key Idea

Before Fabric, a company typically stitched together separate tools for each job — one for pipelines, one for warehousing, one for BI, one for real-time data, one for Spark/data science — each often storing its own copy of the data. Fabric puts all of these under one roof, sharing one single copy of the data underneath everything.

🏢
The "one office building" analogy

Imagine every department (Sales, HR, Finance, Support) used to work out of separate buildings across the city — each with its own filing cabinets, duplicating the same paperwork. Microsoft Fabric is like moving everyone into one office building: Data Engineering has a floor, Data Warehouse has a floor, Real-Time has a floor, Power BI has a floor — but there's one shared records room in the basement that every floor reads from. No department needs its own duplicate copy of the files anymore.

Why is Fabric called a "Unified SaaS Product"? (the PaaS pain it removes)

This is the single most-asked conceptual question. To answer it well, contrast the old PaaS way with Fabric's SaaS way.

📝 The old way (PaaS) — before Fabric existed

To build one data platform, a company had to manually provision 5–6 separate Azure services and wire them together themselves:

Azure Data Factory (ingest) → Azure Data Lake Storage Gen2 (store raw files) → Azure Databricks / Synapse Spark (engineering) → Azure Synapse SQL Warehouse (SQL analytics) → Azure Machine Learning (data science) → Power BI (visualisation).

The problem: every one of these had its own security rules, own billing, own networking setup, and data had to be manually moved/copied between them.

🧩 PaaS approach (before)
  • You provision & size every service yourself (VMs, storage accounts, Spark clusters)
  • Each tool = its own security, billing, networking
  • Manual data movement between tools
  • 5–6 different logins/portals for one platform
📦 Unified SaaS (Fabric)
  • Zero infrastructure setup — no VMs/storage accounts/Spark clusters to manage
  • Single login, single billing — one "Fabric Capacity" powers everyone
  • Engineers, Analysts, Data Scientists, Business users all log into one portal (fabric.microsoft.com)
  • Everyone shares the same pool of compute & storage

OneLake — storage, format & Direct Lake Mode

Every workload above reads and writes to OneLake, a single, logical data lake built into Fabric. Because everything shares OneLake, data doesn't need to be copied and re-copied between tools — this is often called a "zero-copy" pattern.

💡 Simple Example — think "OneDrive, but for data"

OneDrive gives every app on your laptop one shared place to read/write your files, instead of each app keeping its own copy. OneLake does the same job for Fabric's workloads — one shared, organisation-wide data lake that every experience (Warehouse, Engineering, Real-Time, Power BI…) reads from directly. You never manually create a "Storage Account" — Microsoft provisions and manages OneLake transparently behind the scenes.

⭐ Key Idea — the tech under the hood

Underlying tech: OneLake is built on top of Azure Data Lake Storage (ADLS) Gen2. Universal format: every single tool inside Fabric writes its data to OneLake in an open standard called Delta Lake (Delta Parquet). Because everyone writes in the exact same format, data duplication is eliminated — one copy, one format, readable by every engine.

🎯 Interview Point — Direct Lake Mode

Because Power BI and Spark/Python both read/write the same Delta Parquet files in OneLake, Power BI can read data written by a Spark notebook directly, in milliseconds — with no import, no copy, no separate refresh. This is called Direct Lake Mode. Contrast it with the older modes: Import mode (data is copied into Power BI's own memory) and DirectQuery mode (Power BI queries the source live, but slower, query-by-query). Direct Lake gives near-Import speed without the copy.

Is Microsoft Fabric an orchestration tool?

Yes, absolutely. Microsoft Fabric includes Azure Data Factory natively built-in as the Data Pipelines experience — the master orchestration engine that triggers, schedules, and chains tasks together.

Tenant, Capacity & Workspace — Fabric's Hierarchy

Before you touch any Fabric item, DP-700 expects you to know exactly where it "lives". Zoom out one level further than most people do — the full chain actually starts at the Company itself, then narrows down: Company → Tenant → Capacity → Workspace → Items.

Company → Tenant → Capacity → Workspace Widest boundary on the left, narrowest container on the right. Think of it like a real-estate company building offices around the world.
LEVEL 0 · widest
Company

The enterprise business entity itself — e.g. "Retail Company A". The parent boundary everything else sits inside. This is a business concept, not a Fabric setting.

LEVEL 1
Tenant

A single, dedicated instance of Microsoft Entra ID (Azure AD) representing the organisation — the "owner instance". Top-level security & admin boundary: shared user directory, security policies, and domain (e.g. @companyA.com).

LEVEL 2
Capacity

The dedicated engine — a pool of CPU/RAM/storage, bought as an F-SKU (F2…F2048), placed in a specific geographic region. A tenant can have one or many capacities.

LEVEL 3
Workspace

The departmental folder — where teams store actual data assets (Pipelines, Lakehouses, Notebooks, Warehouses, Reports). Every workspace sits inside one capacity.

Retail Company A: ONE tenant → three capacities (US, UK, Germany) → each capacity holds several workspaces (Marketing, Sales, Finance). Retail Company B: split into TWO separate tenants (Military section tenant, Commercial tenant) — each with its own capacities and workspaces.
⭐ Key Idea — Data Sovereignty (why Capacity has a region)

A Capacity isn't just "compute power" — it's also a physical location. If local law in Germany requires user data to stay inside Germany, you create a "Germany capacity". Any workspace hosted inside that capacity will physically store and process its data inside Microsoft's Germany data centers — this is called data sovereignty / data residency, and it's exactly why Company A in the diagram has separate US, UK, and Germany capacities under the same single tenant.

💡 Simple Example — workspace access is scoped

A Workspace is like a departmental folder: Marketing workspace, Sales workspace, Finance workspace. A user placed in the Marketing workspace only sees marketing data — they don't automatically get access to Sales or Finance data unless someone explicitly grants it. Access is scoped per workspace, not company-wide by default.

Decoding the two architecture patterns in the diagram

The image shows two real deployment strategies enterprises actually use. This contrast is a favourite DP-700 scenario question:

🏢 Strategy 1 · Single-Tenant (Company A)
  • 1 Company → 1 tenant → multiple regional capacities (US, UK, Germany) → multiple workspaces
  • Centralised management — one dashboard for everything
  • All employees share the same user directory & licenses
  • Governance & Purview rules managed from one place across all regions
🪖 Strategy 2 · Multi-Tenant (Company B)
  • 1 Company → 2 separate tenants (Military section, Commercial) → their own capacities → their own workspaces
  • Used for strict isolation & security — e.g. government/defense regulations
  • The military division cannot share a security environment, domain, or user directory with the commercial side
  • Complete isolation: commercial admins/users can never see or access military-tenant data
💚 Golden Takeaway

You can deploy multiple capacities across different global regions inside a single tenant purely to satisfy local data-residency requirements — you do not need separate tenants just for geography (Company A proves this). You only reach for separate tenants when the requirement is identity/security isolation, not just location (Company B's case).

Capacity SKUs — sizing the engine

Capacity comes in sizes, each roughly double the compute of the previous one: F2, F4, F8, F16, F32 … up to F2048. The number = Capacity Units (CU) available. Bigger SKU = more Spark cores, more concurrent queries, more throughput. Workspaces don't have their own compute — they borrow it from whichever capacity they're assigned to.

📝 Why "Capacity" and not "Resource"?

In classic Azure, you'd create a separate resource for every single thing (one resource for a VM, another for a storage account, another for a Spark pool) — each billed and scaled on its own. Fabric flips this: you create one Capacity, and every different workload (Warehouse, Pipeline, Notebook…) just gets assigned to that same capacity to borrow its power. One engine, many resources plugged into it — that's why it's named "Capacity", not "a resource".

📝 Bonus DP-700 term — Domains

Between Capacity and Workspace, Fabric also has an optional layer called Domains — a way to group workspaces by business area (Sales, Finance, Operations) for delegated governance, without changing which capacity powers them. Full exam hierarchy: Tenant → Capacity → Domain → Workspace → Items.

🧠 Memory Hook
🧠 Memory Hook

"Company → Country → Building → Office." Company is the whole business. Tenant is its one identity/passport (usually one per company). Capacity is a building it owns in a specific country/region (US, UK, Germany) — the power & utilities. Workspace is the office/floor inside that building where a team actually works. Only split into a second "passport" (tenant) when you need total separation, not just a different country.

🎯 Interview Point

State the full chain cold: "Company is the business entity. Tenant is the Microsoft Entra ID boundary — usually one per company, mapped to its domain. A tenant contains one or more Capacities (compute/billing units, bought as F-SKUs, tied to a specific geographic region for data sovereignty). Each Capacity hosts one or more Workspaces, which contain the actual Fabric items. Domains optionally group workspaces for governance." Also know: a workspace belongs to exactly one capacity at a time; region choice for a capacity is usually driven by data residency/compliance, while a second tenant is driven by security isolation.

Fabric Workspace Roles

Once you're inside a Workspace (the departmental folder from Section 02), Fabric controls exactly what each person can do there through 4 roles: Admin, Member, Contributor, Viewer. Each step down the ladder removes one power.

Official capability matrix. Notice the pattern: Admin-only powers (top rows), Admin+Member powers (middle rows), then everyone-can-view powers (bottom row).
👑 Admin — "The Boss"full control
Complete administrative control over the workspace and everything inside it.
  • Delete or update the workspace itself
  • Add/remove people — including making other users Admins
  • Assign or change the workspace's capacity (F-SKU)
  • Everything a Member/Contributor/Viewer can do, plus all of the above
Who gets this: Lead Engineers, Platform Administrators, Team Managers.
🤝 Member — "Co-Owner"create + share
Full content creation & collaboration power, but no control over workspace-level settings or Admins.
  • Add people with lower permissions (Contributor/Viewer)
  • Create/edit all items — mirroring, SQL databases, warehouses, lakehouses, pipelines, reports
  • Reshare items and publish reports/apps externally

Cannot: delete the workspace, or add/manage other Admins.

Who gets this: Senior Analytics Engineers, Data Architects, Senior Analysts.
🛠️ Contributor — "The Developer"build, no share
Can build & run things, but has zero power over people or sharing.
  • Create, edit, delete items — pipelines, notebooks, lakehouses, warehouses, SQL DBs, reports
  • Run pipelines, execute queries, train ML models

Cannot: add/remove users, reshare items, or touch workspace permissions.

Who gets this: Data Analysts, Data Engineers, Software Developers, ML Engineers.
👁️ Viewer — "Business User"read-only
Strict read-only access — look, don't touch.
  • View reports, dashboards, app content
  • Read data from SQL endpoints/semantic models (if granted data-level access)
  • View metadata for pipelines, notebooks, ML models

Cannot: edit, create, or delete anything — no schema or schedule changes.

Who gets this: Business Managers, Executives, External Stakeholders, End Users.

⭐ Key Idea — each role removes exactly one power

Read the table top to bottom and it's a clean staircase: Admin has workspace control (delete/manage Admins) that Member doesn't. Member can add people & reshare, which Contributor can't. Contributor can create/edit items, which Viewer can't. Every role below still keeps everything the roles below it can do — permissions are strictly nested, nothing skips a step.

🧠 Memory Hook

"Own it → Share it → Build it → See it." Admin owns the workspace, Member shares access & content, Contributor builds the content, Viewer just sees the result. Four verbs, four roles, in order.

🎯 Interview Point

The classic trap question: "What's the difference between Member and Contributor?" → Both can create/edit almost all the same items, but only Member can add people (Contributor/Viewer) and reshare items — Contributor cannot touch sharing or users at all. Another common one: "Can a Viewer see the underlying pipeline code?" → No, Viewers only see metadata and finished reports/dashboards, never the developer-level content.

04

OneLake Deep Dive — Format, Shortcuts & Why It Replaced ADLS Gen2

Section 01 introduced OneLake as "OneDrive for data". Now let's go deep — what data it actually stores, how, and the exact 4 reasons Microsoft built OneLake instead of just handing everyone raw ADLS Gen2.

What kind of data does OneLake accept?

OneLake isn't picky — it accepts all three fundamental types of enterprise data:

TYPE 1
Unstructured

Raw files, PDFs, videos, images — no fixed schema at all.

TYPE 2
Semi-structured

JSON files, XML files, IoT log streams — some structure, but flexible.

TYPE 3
Structured

Tables, relational databases, spreadsheets — strict rows & columns.

💡 Simple Example — the "OneDrive" formula

Think of your own OneDrive. You don't create separate C-drives and D-drives for different file types — there's one main OneDrive folder, with sub-folders inside: Personal, Photos, College Work. Photos holds MP4/JPEG/PNG (unstructured), College Work holds Excel/Word (structured). OneLake is exactly this — just OneDrive scaled up for enterprise big data, with workspaces playing the role of sub-folders.

How structured data is actually stored: Delta Parquet

When structured/semi-structured data lands in OneLake, Fabric stores it internally using Delta Parquet (a.k.a. Delta Lake) — two layers working together:

1
Parquet layer — storage efficiency

Data is written as compressed, columnar Apache Parquet files. Because it's columnar, reading specific columns across millions of rows takes milliseconds, not seconds.

2
Delta Log layer — the _delta_log folder

Alongside the Parquet files sits a JSON-based transaction log that records every insert, update, and delete made to the table.

⭐ Key Idea — why the transaction log matters

That log brings database-like ACID properties to plain big-data files. It lets multiple engines (Spark, SQL Data Warehouse, Power BI) read and write the same table at the same time without corrupting it, and it enables Time Travel — querying an older version of a table as it existed before a change.

Seeing it in action — Lakehouse and Warehouse sharing OneLake

A Data Engineer (Spark/Python) builds a Lakehouse; a SQL Developer (T-SQL) builds a Data Warehouse. Both ultimately land inside OneLake — as separate workspace folders (Workspace POS sales, Workspace expenses).
💡 Simple Example — two roles, one format

Left side (Lakehouse): a Data Engineer writes Python/Spark code that reads unstructured files (CSVs, JSONs, images), cleans them, and converts them into Delta Parquet — landing in the Workspace POS sales folder. Right side (Warehouse): a SQL Developer writes T-SQL. Older data warehouses used their own proprietary storage format, but in Fabric, the Warehouse also writes its data as Delta Parquet underneath — landing in Workspace expenses.

⭐ Key Idea — the magic secret

Because Lakehouse (Spark) and Data Warehouse (SQL) both ultimately write the same open-standard format (Delta Parquet), their data can sit peacefully in different folders of the same OneLake — and any engine can read either one. One format, many engines, zero friction.

If ADLS Gen2 was fine, why did Microsoft build OneLake?

Under the hood, OneLake is built on ADLS Gen2. But raw ADLS Gen2 means managing complex cloud infrastructure by hand. OneLake abstracts all of that into one logical data lake, for four concrete reasons:

🧱
1 · Eliminates data silos & governance overhead old vs new
ADLS Gen2 way: every department (Marketing, Finance, Sales) created its own storage account — VNETs, storage keys, firewalls, cross-account rules took weeks. OneLake way: there is only ONE OneLake per tenant. No storage accounts, network endpoints, or connection strings — teams just create workspaces.
📄
2 · "One Copy of Data" via Shortcuts old vs new
ADLS Gen2 way: if Data Science (Databricks) needed Warehouse data, someone physically copied it into a separate storage account — stale duplicates, huge storage bills. OneLake way: a Shortcut links to data sitting elsewhere (even AWS S3/Google Cloud) — data stays put, every engine reads it as if it were local.
🛡️
3 · Unified security, zero integration work old vs new
ADLS Gen2 way: configure Azure IAM on the storage account, then SQL permissions in Synapse, then workspace permissions in Power BI — three separate setups. OneLake way: permissions are centralised — access a Lakehouse table once, and it works the same from a Notebook, a SQL query, and a Power BI report.
⚡
4 · Direct Lake Mode in Power BI old vs new
ADLS Gen2 way: Power BI had to import data into its own memory engine (VertiPaq) via scheduled refreshes. OneLake way: since everything's already Delta Parquet, Power BI reads it directly, at in-memory speed — no import, no duplication.

Marketing, Finance, Accounts, and HR divisions all need the same Sales Data. The old way meant separate storage per division (and copies of the same data). OneLake's Shortcuts let all four read the one real copy instead.

🔗
Shortcuts = a desktop shortcut, not a copy

If Finance needs Sales' data: the old way was download-then-upload (2 physical copies). The OneLake way — Finance creates a Shortcut, exactly like a Windows desktop shortcut icon that points to a file elsewhere. Finance reads live data without copying a single KB. This is the "One Copy of Data" principle in action.

📝 Bonus — storage redundancy still applies underneath

Because OneLake sits on ADLS Gen2, the usual Azure Storage redundancy tiers still apply for durability: LRS (Locally Redundant — 3 copies in one datacenter), ZRS (Zone-Redundant — copies across availability zones in one region), GRS (Geo-Redundant — LRS + async copy to a paired region), and GZRS (Geo-Zone-Redundant — ZRS + async copy to a paired region). These protect against hardware/datacenter/regional failure — separate concern from Shortcuts (which avoid logical duplication, not physical redundancy).

🧠 Memory Hook

"One Lake, One Format, One Copy." One logical lake (not per-department storage accounts), one format underneath everything (Delta Parquet, so every engine can read it), one copy of data (Shortcuts instead of duplication). Three "ones" — that's the whole pitch of OneLake.

🎯 Interview Point

Be ready for: "OneLake is just ADLS Gen2, so why did Microsoft build it?" → four reasons: (1) eliminates per-department storage-account silos, (2) Shortcuts enable one copy of data instead of manual duplication, (3) unified security across every engine instead of per-tool permission setup, (4) enables Direct Lake Mode for Power BI. Also know the two-layer format: Parquet (columnar storage) + Delta Log / _delta_log (JSON transaction log) = ACID transactions + Time Travel.

05

Delta Parquet Internals — ACID, Time Travel & Concurrency

Section 04 introduced Delta Parquet as "Parquet files + a transaction log". Now let's see exactly what that log does when something goes wrong mid-write — this is where Delta Lake earns the name "Lakehouse".

A real Azure scenario to anchor this

1
Source

An e-commerce system streams live transactions into an Azure Event Hub.

2
Ingestion

An Azure Data Factory (ADF) pipeline reads that stream and writes batch updates every 5 minutes.

3
Storage target

Writes land in an ADLS Gen2 / OneLake folder, as Delta Parquet.

4
Consumers

Power BI reads it for reports; Azure Databricks reads it to run ML algorithms — at the same time.

Decoding the whiteboard — what the checks and the X actually mean

A plain folder holds raw files (data1.parquet, data2.parquet). Delta adds one more thing next to them: a _delta_log folder that tracks which files are actually valid.
✅
data1.parquet committed
ADF successfully writes this file completely. A commit record is added inside _delta_log confirming file 1 is valid.
⚠️
data2.parquet failed mid-write
While writing this file, ADF suffers a network disconnection halfway through. The file physically exists in storage — but it's incomplete and corrupted.
📜
The Delta Log decides what's "real" the fix
In plain Parquet, Power BI/Databricks would blindly read both files — pipeline failures or wrong numbers. In Delta Parquet, the engine checks the log first: since data2 was never marked complete, the log tells every reader "ignore data2.parquet entirely — only read data1.parquet."

Why this makes it a true "Lakehouse" — 3 capabilities

⭐ 1 · ACID Transactions (Atomicity)

Atomicity means an operation either completely succeeds or fully rolls back — no in-between. Without Delta: an ADF batch write that crashes halfway leaves half-written, unreadable files sitting in the folder forever. With Delta: writes are atomic — the uncommitted file simply stays untracked in _delta_log, so every query still sees clean, consistent data (exactly like data2.parquet above).

⭐ 2 · Time Travel & Data Versioning

Every insert/update/delete creates a new JSON commit file inside _delta_log (000000.json, 000001.json, …) — a running history of every change.

💡 Simple Example — undoing a bad pipeline run

An ADF pipeline accidentally runs a bad transformation at 2:00 PM, corrupting a customer metrics table. Instead of restoring a multi-terabyte backup from another region, you just query the table as it was one minute earlier:

Time Travel query — Databricks / Synapse SQL
SELECT * FROM SalesTable
TIMESTAMP AS OF '2026-08-11 13:59:00';

Delta reads the log state exactly as it stood at 1:59 PM, silently ignoring every commit made after that timestamp — no restore, no downtime.

⭐ 3 · Concurrent Reads & Writes

Without Delta: if ADF tries to append new Parquet files while Power BI is actively querying the same folder, Power BI throws a file-lock error. With Delta (Optimistic Concurrency Control): readers query the latest valid, committed state from the log while writers build new files in parallel; once a write finishes, the log updates instantly — no locking, no errors, both sides just work.

Delta Parquet = Apache Parquet Files + _delta_log (Transaction Log) The formula behind every capability in this section.
🧠 Memory Hook

"Log decides what's real." The Parquet files are just raw pages; the _delta_log is the referee. If a write isn't in the log as committed, it doesn't count — no matter what's sitting in storage. Every superpower (ACID, Time Travel, no-lock concurrency) comes from that one referee.

🎯 Interview Point

Golden keywords to drop: Delta Log / _delta_log (transaction log tracking commits, schema evolution, file state), Time Travel (historical auditing / point-in-time recovery via TIMESTAMP AS OF or version number), ACID Transactions (all-or-nothing writes, no partial loads), and DML support — Delta enables native UPDATE, DELETE, and MERGE INTO directly on cloud file storage, which plain Parquet cannot do. If asked "how does Delta know a file is bad?" → it doesn't inspect the file; it simply never finds a commit record for it in the log, so it's treated as if it doesn't exist.

Full chain is actually 4 levels: Company → Tenant → Capacity → Workspace → Items. Company is the business itself, not a Fabric setting.
Data sovereignty: Capacity has a region for a reason — e.g. a "Germany capacity" keeps data physically inside Germany to satisfy local law. One tenant can have many regional capacities.
Single-tenant (Company A) = centralised management, one user directory, one Purview dashboard across all regions. Multi-tenant (Company B) = strict isolation for regulatory reasons (e.g. military vs commercial).
Golden rule: split capacities across regions for data residency; split tenants only for identity/security isolation — not the same reason.
A tenant usually = one org, but can split into multiple tenants for full identity/security isolation (e.g. military vs commercial divisions).
Capacity SKUs: F2, F4, F8 … F2048 (Capacity Units, CU). A workspace is assigned to exactly one capacity at a time for its compute.
4 workspace roles, strictly nested: Admin (owns workspace, manages Admins/capacity) → Member (adds people, reshares, edits all items) → Contributor (creates/edits items, no sharing/users) → Viewer (read-only, metadata + reports only).
Member vs Contributor trap: only Member can add people & reshare items — Contributor can build/edit but never touches sharing or users.
Viewers never see developer code/pipeline internals — only metadata and finished reports/dashboards.
OneLake accepts unstructured (files/video/images), semi-structured (JSON/XML/IoT), and structured (tables/DBs) data — like OneDrive's sub-folders.
Delta Parquet = Parquet layer (columnar, fast reads) + Delta Log (_delta_log JSON transaction log) → gives ACID transactions + Time Travel.
Lakehouse (Spark) and Warehouse (T-SQL) both ultimately write Delta Parquet underneath — that's why they coexist smoothly inside the same OneLake.
4 reasons OneLake replaced raw ADLS Gen2: (1) no per-department storage-account silos, (2) Shortcuts = one copy of data, (3) unified security across engines, (4) Direct Lake Mode for Power BI.
Shortcuts = like a desktop shortcut; point to data elsewhere (other workspace, ADLS Gen2, S3, GCS) without physically copying it.
Storage redundancy still applies under OneLake/ADLS Gen2: LRS, ZRS, GRS, GZRS — physical durability, a separate concern from logical duplication.
A file only "counts" if it has a commit record in _delta_log — a half-written file (network failure mid-write) just gets silently ignored by every reader.
Time Travel: query a table as of a past timestamp/version — SELECT * FROM t TIMESTAMP AS OF '...' — no backup restore needed.
Optimistic Concurrency Control: readers see the latest committed state while writers write in parallel — no file-lock errors, unlike plain Parquet.
Delta enables native UPDATE, DELETE, MERGE INTO on cloud file storage — something plain Parquet files cannot do at all.
